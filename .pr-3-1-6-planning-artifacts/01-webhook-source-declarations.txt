=== webhooks.products.create.tsx — TaggingJob enqueue conditions ===
Lines 31-37: early-return if MerchantConfig.lastFullSyncAt is null
Lines 78-90: TaggingJob enqueue ONLY when topic==PRODUCTS_CREATE AND resourceGid set AND local Product row exists
                Calls enqueueTaggingForProduct(triggerSource='WEBHOOK_CREATE')
                kind defaults to SINGLE_PRODUCT (NOT RE_EMBED)

=== webhooks.products.update.tsx — does NOT enqueue TaggingJob ===
Only enqueues CatalogSyncJob DELTA via enqueueDeltaForShop. By design (PR-2.1):
DELTA path enqueues SINGLE_PRODUCT TaggingJob with triggerSource='DELTA_HASH_CHANGE'
for hashChanged products at app/server/worker-phase-products.ts:158.

=== CRITICAL: enqueueTaggingForProduct never enqueues RE_EMBED ===
app/lib/catalog/enqueue-tagging.server.ts line 32: kind constrained to
SINGLE_PRODUCT or MANUAL_RETAG. Defaults to SINGLE_PRODUCT.
RE_EMBED is enqueued ONLY by:
  - scripts/bulk-reembed-products.ts (3.1.5 survivor; one-shot)
  - mech.6 hand-enqueued verification (MANUAL)
There is NO automatic RE_EMBED trigger on hash change, webhook fire, or cron tick.

=== CRON triggerSource lives on CatalogSyncJob, not TaggingJob ===
app/server/cron-tick.server.ts:153 — triggerSource='CRON' is passed to
enqueueDeltaForShop (CatalogSyncJob), not enqueueTaggingForProduct (TaggingJob).
So 'zero CRON rows in TaggingJob' is by design, not a bug. CRON-driven DELTA
drains will produce DELTA_HASH_CHANGE TaggingJob rows downstream.
