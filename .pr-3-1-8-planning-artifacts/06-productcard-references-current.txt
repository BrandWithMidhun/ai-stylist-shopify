RE-VERIFICATION QUESTIONS (answered):

  Q1: Are v1's and v2's `ProductCard` types now structurally identical?
  A1: YES on the chat-tool contract fields (Type 1 above). v2's type adds
      three optional telemetry fields (traceContributions, whyTrace,
      finalScore) which v1 does not have; these are out-of-band from the
      widget render path and the agent's prompt. Wire-level identical.
      Data-level (post-mech.2): identical formula for variantId,
      compareAtPrice, available.

  Q2: Does the chat widget's OOS check still work against v2's real-boolean
      `available` post-mech.2?
  A2: YES. Line 839's `oos = !product.variantId || product.available === false`
      now correctly resolves:
        - variant loaded + available  → variantId numeric, available=true  → oos=false ("Add to Cart" shown)
        - variant loaded + unavailable→ variantId numeric, available=false → oos=true  ("Out of Stock" shown)
        - no variant loaded           → variantId=null, available=false    → oos=true  (safe failure mode)
      This is the SAME behavior v1 has (v1's formatProductCard at lines 159-160
      uses `extractNumericId(variant.shopifyId)` and `variant?.availableForSale
      ?? false` — identical to v2's post-mech.2 wire).

  Q3: Does any other consumer of `ProductCard` make assumptions that v1
      and v2 violate differently?
  A3: No new such consumer surfaced. The two ProductCard types are still
      used in exactly the same places: agent.server.ts response shaping
      (types.ts:31-43, used to type the tool result's `products?:
      ProductCard[]`), the chat widget render, and the v2 telemetry
      writes (RecommendationEvent.candidates). All other places that
      mention `ProductCard` are comment refs (artifact 03 enumerates them).
