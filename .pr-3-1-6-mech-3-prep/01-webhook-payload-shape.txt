=== Step 0 surface verification — payload shape findings ===

QUESTION: Does the products/update webhook payload include recommendationExcluded?

ANSWER: NO. Definitively no. Surfacing structural finding before code changes.

=== Why ===

`recommendationExcluded` is NOT a Shopify field. It is a custom column on
the AI Stylist app's `Product` table, added in migration
`20260424195530_add_recommendation_excluded_flag`. Shopify has no notion
of this concept — it's purely an internal merchant-facing toggle managed
by the AI Stylist admin UI to decide whether a product appears in
recommendation results.

The Shopify products/update webhook payload contains the standard
Shopify product record (id, title, handle, body_html, vendor, tags,
status, variants, options, images, updated_at, etc.) but cannot
contain `recommendationExcluded` because Shopify doesn't know about it.

=== Sole mutation path ===

Verified via grep: only ONE site in the codebase mutates
`recommendationExcluded`:

  app/routes/api.products.$id.exclude.tsx:44
    data: { recommendationExcluded: parsed.data.excluded }

This is the internal PATCH endpoint that the merchant's AI Stylist
admin UI calls when they toggle the "Exclude from recommendations"
flag on a product (per `specs/005d-product-edit-drawer.md` and
`specs/005c-intelligence-dashboard.md`).

All other references in the codebase are reads (filter conditions,
type definitions, test fixtures) or an optimistic UI update in
Dashboard.tsx that dispatches to the same PATCH endpoint.

=== Implication for mech.3 ===

The mech.3 prompt's wire site assumption is wrong. The plan said:
"Modify app/routes/webhooks.products.update.tsx … compare prior/current
recommendationExcluded from webhook payload."

That cannot work — the webhook payload doesn't carry the field.

The CORRECT wire site is `app/routes/api.products.$id.exclude.tsx`
itself: when the merchant toggles the flag and the route writes
`recommendationExcluded: false` (after it was previously `true`),
enqueue RE_EMBED there. That is structurally cleaner than a webhook
detour:
  - Single-place change, in code we already own
  - Deterministic prior-state lookup (read the current row before
    update; no webhook delivery races)
  - Authenticated context (the route already calls
    `authenticate.admin(request)`)
  - No transaction-boundary concerns (the route uses a single
    `prisma.product.updateMany`, RE_EMBED enqueue can sit after
    the write)
